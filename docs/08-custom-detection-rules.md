# Custom Detection Rules

## Objective

The objective of this phase was to create and validate a custom Wazuh detection rule using Sysmon process creation telemetry.

The goal was to demonstrate detection engineering by identifying a specific Windows process that was visible in collected telemetry but did not generate a dedicated Wazuh alert by default.

For this controlled test, the target process was:

```text
notepad.exe
```

---

## Why a Custom Rule Was Needed

Microsoft Sysmon was configured to generate detailed process creation telemetry.

When Notepad was launched on the monitored Windows endpoint, Sysmon successfully generated:

```text
Event ID 1 — Process Creation
```

The event was collected by the Wazuh agent and forwarded to the Wazuh manager.

However, simply collecting an event does not guarantee that Wazuh will generate a security alert.

A matching detection rule is required.

To demonstrate this distinction, a custom rule was created specifically for Notepad process creation.

---

## Detection Data Source

The custom rule uses:

```text
Microsoft Sysmon
Event ID: 1
Event Type: Process Creation
```

The Sysmon event contains information including:

- Process image
- Command line
- Parent process
- Parent command line
- User
- Process ID
- Integrity level
- Process creation timestamp

The process image field was used as the primary matching condition.

---

## Custom Rule

The custom rule was added to:

```text
/var/ossec/etc/rules/local_rules.xml
```

The implemented rule was:

```xml
<rule id="100100" level="5">
  <if_group>sysmon_event1</if_group>
  <field name="win.eventdata.image" type="pcre2">(?i)notepad\.exe$</field>
  <description>Custom Detection: Notepad process created</description>
  <group>sysmon,process_creation,custom_detection,</group>
</rule>
```

---

## Rule Explanation

### Rule ID

```text
100100
```

A custom rule ID was used so the detection could be easily identified during testing and investigation.

### Rule Level

```text
5
```

The rule was assigned level 5 for lab detection and validation purposes.

It should not be interpreted as meaning that Notepad itself is malicious.

---

## Sysmon Event Condition

The following condition restricts the rule to Sysmon Process Creation events:

```xml
<if_group>sysmon_event1</if_group>
```

This ensures that the detection evaluates events belonging to the Sysmon Event ID 1 rule group.

---

## Process Image Matching

The following field condition identifies Notepad:

```xml
<field name="win.eventdata.image" type="pcre2">(?i)notepad\.exe$</field>
```

The expression matches process image paths ending in:

```text
notepad.exe
```

The `(?i)` modifier makes the match case-insensitive.

The `$` ensures that the executable name appears at the end of the process image path.

For example:

```text
C:\Windows\System32\notepad.exe
```

matches the detection condition.

---

## Rule Description

The alert generated by the rule uses:

```text
Custom Detection: Notepad process created
```

This makes the purpose of the rule clear when reviewing alerts in the Wazuh Dashboard.

---

## Detection Workflow

The custom detection pipeline was:

```text
Notepad.exe
     │
     ▼
Sysmon Event ID 1
     │
     ▼
Wazuh Agent
     │
     ▼
Wazuh Manager
     │
     ▼
Custom Rule 100100
     │
     ▼
Wazuh Alert
```

---

## Configuration Validation

After adding the custom rule, the Wazuh configuration was validated before testing.

The Wazuh manager was then restarted so that the custom detection rule would be loaded.

This ensured that the rule configuration was accepted before detection testing continued.

---

## Detection Testing

The rule was tested by launching Notepad normally on the monitored Windows endpoint.

```cmd
notepad.exe
```

The resulting sequence was:

1. Windows launched `notepad.exe`.
2. Sysmon generated Process Creation Event ID 1.
3. The Wazuh agent collected the Sysmon event.
4. The event was forwarded to the Wazuh manager.
5. Custom Rule `100100` evaluated the process image.
6. The rule matched `notepad.exe`.
7. Wazuh generated the custom alert.

---

## Validation Result

The Wazuh Dashboard showed:

```text
Agent: SP-WIN-01
Rule ID: 100100
Rule Level: 5
Description: Custom Detection: Notepad process created
```

This confirmed that the custom detection rule was functioning successfully.

---

## Detection Engineering Significance

Notepad was intentionally selected as a harmless process for controlled testing.

The purpose of the rule was not to classify Notepad as malicious.

Instead, it demonstrated the detection engineering process:

```text
Identify Telemetry
       │
       ▼
Choose Detection Condition
       │
       ▼
Create Rule
       │
       ▼
Validate Configuration
       │
       ▼
Generate Test Activity
       │
       ▼
Observe Alert
       │
       ▼
Validate Detection
```

The same workflow can be applied to more security-relevant behaviors when developing production detections.

---

## Connection to Active Response

Custom Rule `100100` was later used as the trigger for the project's safe Active Response demonstration.

The resulting workflow became:

```text
Notepad.exe
      │
      ▼
Sysmon Event ID 1
      │
      ▼
Custom Rule 100100
      │
      ▼
Wazuh Alert
      │
      ▼
Active Response
      │
      ▼
Custom Python Script
```

The Active Response executed only on the Ubuntu Wazuh manager and created a harmless temporary marker file.

This allowed the project to demonstrate the connection between:

```text
Telemetry → Detection → Alert → Automated Response
```

without making disruptive changes to the Windows endpoint.

## Key Takeaways

The custom detection demonstrated an important SIEM concept:

> Collecting telemetry and generating alerts are different stages of the monitoring pipeline.

Sysmon provided the process creation telemetry, while the custom Wazuh rule converted selected telemetry into a security alert.

The successful detection of `notepad.exe` confirmed that custom detection logic could be developed, deployed, tested, and validated within the SOC homelab.

This completed the custom detection engineering phase and provided the trigger later used for the safe Active Response demonstration.
